# Database migration safety

The new migrations are additive: audit events, nullable archive/scan metadata, filter indexes, token blacklist tables, pgvector extension, nullable vector column, and HNSW index. Existing migration history was not rewritten. Adding indexed fields can scan/lock large tables; on a populated deployment, first add nullable/unindexed columns, backfill in bounded batches, then create PostgreSQL indexes concurrently in a follow-up release. The current migrations are appropriate for a new/small initial deployment but require that phased treatment once tables are large.

Pre-deploy: take and verify a backup, measure table sizes and locks, enable `vector`, run `migrate --plan`, and verify the embedding dimension is 1536. Deployment: use a single release job to run `migrate --noinput` before new workers, with old code remaining compatible with nullable fields. Post-deploy: backfill vectors, compare retrieval, analyse tables, and only then enable pgvector traffic. Rollback cannot remove columns referenced by newly written rows; roll application code back first. Extension/index removal is not a data rollback. Never reverse archival fields if archived records exist.
